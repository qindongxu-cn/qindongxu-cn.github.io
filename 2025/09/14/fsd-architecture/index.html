类 FSD 架构：是什么、如何落地、为何更优

背景与定义

随着前端项目复杂度不断提升，传统以“技术栈”或“页面”划分目录的方式逐步暴露出维护成本高、模块边界模糊、协作困难等问题。类 FSD（Feature-Sliced Design）架构以“业务特性”为第一维度切分代码，通过明确层次与依赖方向，让团队更容易组织大型前端项目。

类 FSD 并非僵化的框架，而是一套可落地的模块化设计理念：先根据业务能力划分“特性”，再在每个特性内部按职责拆分文件与组件，保证业务场景的封装性与可扩展性。

传统架构痛点与 FSD 优势

传统前端目录通常是 components/、pages/、utils/、api/、store/ 的组合，初看简单，实际使用会暴露诸多问题：

components/
pages/
utils/
api/
store/
  • 组件目录越写越乱：components/ 里从基础 Button 到业务级 ProductCard、评论区组件都往里丢，久而久之难以界定边界，任何改动都需要小心翼翼地检索引用。
  • 业务逻辑四处散落：以购物车为例，页面逻辑在 pages/，计算工具在 utils/，状态在 store/，组件在 components/，函数跨目录调用，维护者需要“跨图作战”。
  • 耦合度高导致重构艰难：修改 ProductCard 可能牵动五个页面；想抽取能力时发现依赖回环、全局变量满天飞，重构成本指数级上升。
  • 到了后期： 没人知道该把东西放哪，维护成本飞涨。

类 FSD 架构从根源解决这些痛点：

  • 业务独立的特性目录：每个 Feature 自带 ui、model、api，例如 features/login/ 下集中所有登录逻辑，定位问题一目了然。
  • 清晰的依赖层级：约定 shared → entities → features → widgets → pages → app 的单向依赖，结合 lint 规则，一旦越级引用即可在开发期发现。
  • 高复用性与可迁移性：特性遵循统一结构，features/filter/ 可以随时被其他页面引用；实体数据层 entities/ 则提供稳定接口。
  • 便于多人协作：不同同事负责不同 Feature，不再挤在同一目录“抢地盘”，互动冲突和 Review 成本显著下降。
  • 重构与扩展更轻松：边界清晰、封装良好，新业务只需新增 Feature/Entity，旧逻辑重构时也只在局部范围内调整。

是否采用 FSD，可结合项目规模评估：多人协作、长期迭代、业务复杂、复用逻辑多、页面多或拥有多条产品线时收益最大；若仅有 2-3 个页面的小项目，则没必要引入完整 FSD 体系。

核心原则

  • 自顶向下的分层约束：高层（如 app、pages）只组合低层模块，低层不反向依赖，形成清晰依赖图。
  • 按特性组合能力：围绕“业务动作”构建 features，数据与 UI 组合在一起，减少四散的逻辑。
  • 实体驱动建模：entities 层沉淀核心业务模型及其基础视图，便于复用与演进。
  • 共享资源最小化：shared 仅放置真正通用的工具、UI 库和 API 客户端，避免成为“垃圾场”。
  • 可演进的边界：目录和层级允许随着业务成长调整，保持规约与灵活性的平衡。

分层结构速览

典型的类 FSD 项目自外向内可划分为：

  • app：应用入口、全局配置、国际化、错误边界。
  • processes：跨页面的长流程（如注册签约、支付链路）。
  • pages：页面容器，负责路由与数据装配，不承担业务实现。
  • widgets：跨多个页面复用的组合型 UI（导航栏、仪表盘）。
  • features：可复用的业务功能单元（评论提交、文件上传）。
  • entities：业务实体模型与其最小视图（用户卡片、订单状态）。
  • shared：工具函数、主题系统、API 客户端、基础组件库。

前端落地步骤

  1. 梳理业务特性：列出核心流程与实体，明确每个特性在业务中的目标与边界。
  2. 定义依赖规则：约定只能“自上而下”引用，并配合 ESLint/TSPath 等工具校验。
  3. 搭建目录骨架：在仓库中创建基础层级，准备示例模块和脚手架命令。
  4. 增量迁移代码：优先迁移高变业务或新特性，拆出 features 与 entities，避免一次性重构。
  5. 沉淀复用资产：逐步将通用逻辑下沉至 shared，保持结构洁净。
  6. 配合工程工具：结合 Storybook、Jest、CI 校验等手段，确保切片后的模块可独立测试与交付。

Vue 项目目录示例

以 Vue 3 + Vite 项目为例，按类 FSD 思路可将 src/ 目录组织如下：

src/
  app/
    providers/        # 状态注入、国际化、全局错误边界
    router/           # 路由配置与守卫
    store/            # Pinia/Redux 等全局状态入口
    index.vue         # 应用根组件

  pages/
    home/
      ui/             # 页面级布局与组合组件
      model/          # 页面数据装配、路由参数解析

  widgets/
    user-profile/
      ui/             # 头像卡片、基本信息展示
      model/          # 组合特性并连接实体

  features/
    login/
      ui/             # 登录表单、交互逻辑
      model/          # 状态、表单校验
      api/            # 登录请求封装

  entities/
    user/
      model/          # 用户实体类型、状态管理
      lib/            # 用户领域工具函数

  common/
    features/         # 跨应用特性能力，如 message、modals
    entities/         # API 定义，与后端资源保持命名一致
    services/         # 通用 boot 逻辑，埋点、多语言、Store 初始化等

  shared/
    ui/               # 基础通用组件（Button、Modal）
    lib/              # 工具函数、hooks
    api/              # HTTP 客户端、拦截器
    config/           # 常量、环境配置

实践中可以借助 pnpm dlx degit、plop 等脚手架工具生成特性模板，确保每个目录拥有统一的 ui、model、api 结构。React 项目也可采用类似层级，结合 tsx 文件与自定义 hooks，保证跨框架的一致性与可维护性。

Common 子项目的角色

  • Features：封装跨业务的通用特性，例如消息提示 message、模态弹窗 modals，按 FSD 约定继续拆分 ui、model、api。
  • Entities（API）：统一维护对接后端的资源封装，保证文件结构与接口命名一一对应，方便多团队共享。
  • Services：承载项目启动阶段的基础服务逻辑，如埋点初始化、多语言加载、API 客户端实例化、顶层状态注册，确保各业务线遵循同一套启动流程。

与传统架构的差异

维度类 FSD 架构传统按层/按页面架构
划分方式以业务特性为主轴，层级清晰以技术栈或页面划分，边界模糊
依赖管理强制单向依赖，易于追踪组件互相引用，易形成网状耦合
团队协作特性可分包交付，职责明确需跨目录协作，沟通成本高
可维护性特性内聚，改动范围可控修改常牵扯多处，回归成本大
扩展性新业务直接新增特性/实体扩展常需调整多层目录结构
工程配套易结合自动化测试、CI 规则规范难统一，易累积“灰色地带”

实践建议与案例

  • 适合场景：中大型单页应用、业务线众多的 B 端系统、需要长期迭代的复杂产品。
  • 渐进式引入：不要强行一次迁移，可先将新业务按 FSD 架构开发，再逐步拆旧模块。
  • 规范化工具：使用 ESLint 插件或自定义脚本限制跨层引用；配合 TypeScript 路径别名提升可读性。
  • 文档与示例：为团队提供模板文件、目录脚手架与最佳实践清单，降低上手门槛。
  • 持续回顾：定期评估 shared 是否过载、特性是否过大，及时调整边界。

总结

类 FSD 架构以业务切片为核心，让前端团队在应对复杂需求时仍能保持模块清晰和交付高效。通过合理的分层、明确的依赖规则以及工程化约束，它相比传统架构拥有更好的可维护性与扩展性。结合团队现状循序渐进地落地，才能真正释放其价值。
