前端项目容器化 CI/CD 配置指南：从入门到实战

这份文档将带你理解一套通俗易懂、可复用的前端 CI/CD（持续集成/持续部署）方案。这套方案的核心思想是：“配置即代码，环境全打包”。

1. 核心理念：像点外卖一样发版

没有 CI/CD 之前，上线就像自己在家做饭：买菜、洗菜、炒菜、端上桌，每个步骤都可能出错，而且每个人的厨房（开发环境）都不一样。

有了 CI/CD 之后，上线就像全自动中央厨房：

  1. 提交代码 (下单)：你只需要把写好的代码（菜单）提交上去。
  2. CI 流水线 (流水线制作)：GitLab Runner 自动在一个干净的容器里安装依赖、打包代码。
  3. Docker 镜像 (打包成盒)：把打包好的静态文件 + Nginx 服务器 + 配置文件，一起封进一个 Docker 镜像里。
  4. CD 部署 (骑手配送)：把镜像推送到服务器集群，自动替换旧版本。

2. Docker 基础：为什么前端项目需要容器化？

2.1 Docker 是什么？

Docker 是一个开源的容器化平台，它可以把应用程序及其所有依赖（代码、运行时、系统工具、库等）打包成一个轻量级、可移植的容器。

简单理解：Docker 就像是一个标准化的快递箱，无论里面装的是什么（前端项目、后端服务、数据库），都能用同样的方式打包、运输、部署。

2.2 为什么前端项目需要 Docker？

很多前端开发者会问：“前端不就是静态文件吗？为什么需要 Docker？”

答案：前端项目不仅仅是静态文件，还包括：

  1. 运行环境：需要 Nginx 服务器来提供 HTTP 服务
  2. 配置文件：需要 nginx.conf 来支持 SPA 路由
  3. 构建环境：需要 Node.js 来编译代码（虽然最终镜像里不需要）
  4. 版本管理：需要能快速回滚到任意版本

不使用 Docker 的传统方式：

开发 → 本地 npm run build → 手动上传 dist/ → 服务器配置 Nginx → 重启服务

使用 Docker 的方式：

开发 → 提交代码 → CI 自动构建镜像 → 服务器拉取镜像 → 启动容器

优势明显：

  • ✅ 自动化，无需人工干预
  • ✅ 环境一致，不会出错
  • ✅ 快速回滚，秒级切换
  • ✅ 配置即代码，版本可控

2.3 Docker 的三大核心作用

作用 1：环境标准化（一次构建，到处运行）

传统部署的问题：

开发环境：Node 16 + npm 8 + Ubuntu 20.04
测试环境：Node 18 + npm 9 + CentOS 7  ← 环境不一致！
生产环境：Node 14 + npm 6 + Ubuntu 18.04  ← 又不一样！

使用 Docker 后：

# Dockerfile 定义了统一的环境
FROM node:18-alpine AS builder  # 构建环境统一
FROM nginx:1.20-alpine          # 运行环境统一

无论镜像在哪里运行（开发、测试、生产），环境完全一致，不会出现”在我机器上能跑”的问题。

作用 2：依赖隔离（避免环境冲突）

传统部署：

  • 服务器上可能同时运行多个项目
  • 项目 A 需要 Node 16，项目 B 需要 Node 18
  • 全局安装的依赖可能互相冲突

使用 Docker 后：

  • 每个项目运行在独立的容器中
  • 容器之间完全隔离，互不影响
  • 项目 A 用 Node 16，项目 B 用 Node 18，完全没问题

作用 3：快速部署与回滚（秒级切换）

传统部署：

# 部署新版本需要：
1. SSH 连接服务器（30秒）
2. 备份旧代码（1分钟）
3. 上传新代码（2分钟）
4. 安装依赖（3分钟）
5. 重启服务（30秒）
总计：约 7 分钟

使用 Docker 后：

# 部署新版本只需要：
1. docker pull 新镜像（30秒）
2. docker stop 旧容器（1秒）
3. docker run 新容器（1秒）
总计：约 32 秒

# 回滚更简单：
docker run 旧镜像（1秒）

2.4 Docker 镜像 vs 传统部署对比

维度传统部署Docker 容器化
环境一致性❌ 各环境可能不同✅ 完全一致
部署速度⏱️ 5-10 分钟⚡ 30 秒-1 分钟
回滚速度⏱️ 需要手动恢复⚡ 秒级回滚
资源占用💾 每个项目独立环境💾 共享系统资源
隔离性⚠️ 可能互相影响✅ 完全隔离
可移植性❌ 绑定特定服务器✅ 任意环境运行

3. CI/CD 完整流程解析

3.1 流程概览

让我们看看 Docker 在整个 CI/CD 流程中扮演的角色：

┌─────────────────────────────────────────────────────────┐
│                    CI/CD 完整流程                        │
└─────────────────────────────────────────────────────────┘

1. 开发者提交代码
   ↓
2. GitLab CI 触发构建（.gitlab-ci.yml）
   ↓
3. 【Docker 构建阶段】←─── 这里！
   ├─ 执行 build.js 脚本
   ├─ 调用 docker build 命令
   ├─ 读取 Dockerfile
   ├─ 构建 Docker 镜像（包含代码 + Nginx + 配置）
   └─ 推送镜像到镜像仓库
   ↓
4. 【Docker 运行阶段】←─── 还有这里！
   ├─ 服务器拉取镜像
   ├─ docker run 启动容器
   └─ 容器内 Nginx 提供服务
   ↓
5. 用户访问应用

3.2 Docker 镜像的生命周期

让我们看看一个 Docker 镜像从创建到运行的完整过程：

# 1. 构建阶段（在 CI 中执行）
docker build -t my-app:dev-abc123 .
# 这个过程会：
#   - 读取 Dockerfile
#   - 执行第一阶段：安装依赖、编译代码
#   - 执行第二阶段：复制文件、配置 Nginx
#   - 生成最终镜像（通常只有 20-50MB）

# 2. 推送阶段（在 CI 中执行）
docker push my-registry.com/my-app:dev-abc123
# 镜像被推送到镜像仓库（类似 Git 仓库，但存的是镜像）

# 3. 拉取阶段（在服务器上执行）
docker pull my-registry.com/my-app:dev-abc123
# 服务器从仓库拉取镜像到本地

# 4. 运行阶段（在服务器上执行）
docker run -d -p 80:80 my-app:dev-abc123
# 启动容器，映射端口，应用开始提供服务

4. 四大核心文件详解

要实现这套流程，你的项目根目录下通常需要这 4 个文件。你可以直接复制这些模板到新项目中使用。

📂 4.1 总指挥：.gitlab-ci.yml

作用：告诉 GitLab CI 什么时候开始干活，分为哪几步。

# .gitlab-ci.yml
stages:
  - build # 阶段一：构建
  - deploy # 阶段二：部署

# 构建任务
build_app:
  stage: build
  image: node:18-alpine # 指定干活的环境（比如要有 Node.js）
  script:
    - echo "开始安装依赖..."
    - npm install
    - echo "开始构建代码..."
    # 这里我们不直接写复杂的 shell 命令，而是调用一个 JS 脚本来处理复杂逻辑
    - node ./build.js --branch=$CI_COMMIT_REF_NAME --commit=$CI_COMMIT_SHORT_SHA
  # 产物留存（如果不打 Docker 镜像，可以用 artifacts 保留 dist 目录）
  # artifacts:
  #   paths:
  #     - dist/
  only:
    - main # 只有 main 分支提交才触发
    - dev

🛠️ 4.2 逻辑处理师：build.js

作用：为什么不直接在 yaml 里写命令？因为真实项目往往很复杂（区分国内/海外、测试/生产、动态版本号）。用 JS 写脚本比写 Shell 更灵活。

// build.js 通用模板
const { spawn } = require("child_process");

// 获取命令行参数
const args = process.argv.slice(2).reduce((acc, curr) => {
  const [key, val] = curr.split("=");
  acc[key.replace(/^--/, "")] = val;
  return acc;
}, {});

console.log("当前构建参数:", args);

// 核心：调用 Docker 命令
async function build() {
  // 1. 构造 Docker 镜像名称（例如：my-app:dev-a1b2c3d）
  const imageName = `my-registry.com/my-app:${args.branch}-${args.commit}`;

  // 2. 构造 docker build 命令
  // 注意：这里把一些构建时的参数传给 Dockerfile
  const cmd = `docker build -t ${imageName} --build-arg COMMIT_ID=${args.commit} .`;

  console.log("执行命令:", cmd);

  // 3. 执行命令（这里简化了 spawn 的调用，实际使用建议封装一个 runCommand 函数）
  // await runCommand(cmd);
  // await runCommand(`docker push ${imageName}`);
}

build();

📦 4.3 包装说明书：Dockerfile

作用：定义怎么把代码变成镜像。推荐使用多阶段构建（先用 Node 打包，再用 Nginx 运行），这样镜像体积最小。

# --- 第一阶段：构建 (Builder) ---
FROM node:18-alpine AS builder

WORKDIR /app

# 1. 先拷 package.json 好的依赖（利用 Docker 缓存加速）
COPY package.json pnpm-lock.yaml ./
RUN npm install -g pnpm && pnpm install

# 2. 拷源码并打包
COPY . .
# 接收 build.js 传进来的参数
ARG COMMIT_ID
ENV VITE_COMMIT_ID=${COMMIT_ID}
RUN pnpm run build

# --- 第二阶段：运行 (Runner) ---
FROM nginx:1.20-alpine

# 1. 把第一阶段打包好的 dist 目录，拷到 Nginx 的服务目录
COPY --from=builder /app/dist /usr/share/nginx/html

# 2. 【关键】把项目里的 nginx.conf 拷进去替换默认配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 3. 启动 Nginx
CMD ["nginx", "-g", "daemon off;"]

📜 4.4 路由规则书：nginx.conf

作用：前端单页应用（SPA）必须配置，否则刷新页面会 404。这个文件是随代码一起提交的。

server {
    listen 80;
    server_name localhost;
    root /usr/share/nginx/html; # 对应 Dockerfile 里的目录

    # 静态资源缓存（加速加载）
    location ~ .*\.(gif|jpg|jpeg|png|css|js|ico)$ {
        expires 30d;
        add_header Cache-Control "public";
    }

    # 【核心配置】SPA 路由支持
    # 解释：无论用户访问 /user 还是 /settings，都先找有没有这个文件
    # 如果没有，就统统返回 index.html，让前端路由（Vue Router/React Router）去处理

    location / {
        try_files $uri $uri/ /index.html;
        index index.html;
    }
}

5. 深度解析：为什么 Nginx 配置要写在前端项目里？

很多初学者会有疑问：“Nginx 不是服务器软件吗？配置文件 nginx.conf 不应该是在服务器的 /etc/nginx/ 目录下吗？为什么会出现在前端代码仓库里？”

这是一个非常好的问题，它触及了容器化部署的核心优势。

5.1 核心原理：它不是”传”上去的，是”打包”带走的

在传统的部署模式下，你确实需要把代码传到服务器，然后求运维大哥帮你改服务器上的 Nginx 配置。

但在 Docker/K8s 的容器化模式下，逻辑完全变了：

  1. 前端项目 = 代码 (HTML/JS/CSS) + 运行环境 (Nginx) + 环境配置 (nginx.conf)。
  2. Dockerfile 就像一个打包清单，它会做三件事：
    • 把代码编译成静态文件。
    • 下载一个纯净的 Nginx 环境。
    • 关键步骤：把你项目里的 nginx.conf 复制进去，覆盖掉 Nginx 默认的配置。
# Dockerfile 片段
FROM nginx:1.20-alpine
# ...
# 这一行就是"偷梁换柱"，用你项目里的配置，替换掉镜像里默认的配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

5.2 这样做的三大好处

  1. 配置即代码 (Configuration as Code)

    • 前端路由（比如 /user/profile）通常需要 Nginx 配合（配置 try_files）。
    • 如果配置在服务器上，前端改了路由，运维没改配置，线上就崩了。
    • 现在：配置就在代码里，前端改代码的同时顺手改配置，一起提交，一起生效，完全不依赖运维。

  2. 环境一致性

    • 以前经常发生：开发环境（本地 Nginx）是好的，测试环境（运维配的 Nginx）挂了。
    • 现在：因为 Nginx 配置是打包在镜像里的，无论这个镜像跑到开发、测试还是生产环境，它内部的 Nginx 行为永远是一模一样的。

  3. 版本回滚

    • 如果你把代码回滚到上个版本，Docker 镜像也会回滚。
    • 因为旧版本的镜像里，包着旧版本的 nginx.conf，所以配置也自动回滚了。不用担心代码退回去了，配置还是新的导致报错。

6. 如何在其他项目复用？

如果你接手了一个新项目，想接入这套流程，只需做以下 4 步：

  1. 复制文件：把 build.js, Dockerfile, nginx.conf 复制到项目根目录。
  2. 修改 Nginx 路径：检查 Dockerfile 里 COPY --from=builder 的源路径（是 /app/dist 还是 /app/build？）。
  3. 配置 CI：在根目录新建 .gitlab-ci.yml，引用 build.js。
  4. 检查端口：确认 nginx.conf 监听的端口（通常是 80）与 Dockerfile 暴露的端口一致。

7. 常见疑问解答

Q: 为什么要手动写 nginx.conf 放在项目里？

A: 为了环境一致性。如果依赖运维在服务器上手工配置 Nginx，很容易出现”开发环境好的，线上 404”的情况。把配置放进代码仓库，随镜像一起分发，能保证任何地方运行效果都一样。

Q: build.js 是必须的吗？

A: 不是。如果逻辑简单，直接在 .gitlab-ci.yml 的 script 里写 docker build 命令也可以。但当涉及多环境（测试/预发/生产）、多区域（国内/海外）、自动通知（构建完发飞书消息）等复杂逻辑时，用 JS 脚本会好维护得多。

Q: 为什么前端项目需要 Docker？直接上传 dist 目录不行吗？

A: 可以，但不推荐。直接上传 dist 目录的问题：

  • ❌ 需要手动配置服务器上的 Nginx
  • ❌ 不同环境配置可能不一致
  • ❌ 回滚困难，需要手动恢复
  • ❌ 无法保证环境一致性

使用 Docker 的优势：

  • ✅ 配置即代码，随镜像一起分发
  • ✅ 环境完全一致，开发/测试/生产一模一样
  • ✅ 秒级回滚，docker run 旧镜像即可
  • ✅ 自动化部署，无需人工干预

Q: Docker 镜像会不会很大？

A: 不会。使用多阶段构建后，最终镜像通常只有 20-50MB：

  • 构建阶段（builder）：包含 Node.js，可能 200MB+
  • 运行阶段（runner）：只包含 Nginx + 静态文件，只有 20-50MB

最终镜像只包含运行阶段的内容，所以体积很小。

Q: 本地开发也需要 Docker 吗？

A: 不是必须的。本地开发可以直接用 npm run dev 或 vite。Docker 主要用于：

  • CI/CD 构建和部署
  • 生产环境运行
  • 测试环境验证

如果你想在本地也使用 Docker，可以运行 docker build 和 docker run，但通常没必要。
